## What was just built (commit `0b184d4`)

1. **Moonraker API-key auth.** `Moonraker.kt` takes an optional `apiKey` in its
   constructor. It's applied via an OkHttp `addInterceptor` on the client, so it
   covers *every* request path — including `configFile()`, `writeConfig()`,
   `thumbnail()`, `image()`, which call `client.newCall(...)` directly and bypass
   the shared `request()` helper. Don't add a new direct-call method without
   remembering the interceptor already covers it; don't re-add per-method auth
   logic.
2. **Distinct 401/403 messages**: "no key configured" vs "configured key was
   rejected" (see `request()` in `Moonraker.kt`). There's a JVM test for each.
3. **Encrypted credential storage.** New `CredentialStore.kt` wraps
   `androidx.security.crypto.EncryptedSharedPreferences` (Keystore-backed). API
   keys are **never** written into the plaintext `profilesV1` JSON blob in
   `PrinterPreferences.kt` — they live only in the encrypted store, keyed by
   printer address. `PrinterPreferences.profiles()`/`saveProfiles()` both now take
   an extra `secrets: SharedPreferences` parameter for this reason.
4. **Tailscale support in `Moonraker.parseAddress()`**: the CGNAT range
   `100.64.0.0/10` and `*.ts.net` MagicDNS hostnames are now accepted over plain
   `http://`, alongside the existing private-IPv4/`.local`/`localhost` allowances.
   Cloudflare Tunnel / port forwarding / OctoEverywhere need **no client code** —
   they just present as an ordinary `https://` address, which already worked.
5. **UI**: `ProfileEditor` in `M1Panels.kt` has a new masked "API key (optional)"
   field with a Show/Hide toggle, plus a one-line hint about Tailscale/Cloudflare/
   VPN addresses. `save` callback is now `(String,String,String,String)->String?`
   (address, name, apiKey added as 4th param — check every call site if you touch
   this signature again).
6. **Every place that builds its own `Moonraker` client got the API key wired
   in** — not just the main connection. This was the actual bulk of the work.
   Check `PrinterModel.kt`, `MainActivity.kt` (the 7 panel factories:
   console/mesh/toolheads/fanStatus/config/configWriter/speedFlow),
   `HeaterPanel.kt`, `FanPanel.kt`, `LedPanel.kt`, `MacroReviewPanel.kt`,
   `PrinterTiles.kt` (added an `apiKey` field to the `PrinterTile` data class),
   and `SnapshotCamera.kt` (added an `apiKey` param). `MjpegCamera.kt` and
   `LiveCamera.kt` were deliberately **not** touched — those are separate
   camera-streaming services (mjpg-streamer / camera-streamer), not Moonraker
   endpoints, so an `X-Api-Key` header wouldn't mean anything there.
7. New dependency: `androidx.security:security-crypto:1.1.0` in
   `app/build.gradle.kts`.
8. Tests: `MoonrakerTest.kt` got 5 new/renamed cases (header sent, blank key sends
   no header, missing-vs-rejected-key message wording, Tailscale acceptance +
   the CGNAT boundary at `100.128.x.x`). `CompanionScreenTest.kt` got a new
   `profileEditorSendsApiKeyToSave` case and the existing profile-round-trip test
   now also exercises a `secrets` prefs file.
9. Verified live on-device on the owner's Razr 2023: added a fake profile,
   entered an API key, backgrounded/reopened the editor to confirm it persisted

## A Kotlin gotcha you will probably hit if you touch `PrinterModel.kt`

`PrinterModel`'s primary constructor has a parameter literally named
`serviceFactory: ((String) -> PrinterService)? = null`. There is **also** a
class-body property `resolvedServiceFactory` that resolves it against a default
that looks up the profile's API key. They are named *differently on purpose*.

Kotlin's rule: a plain (no `val`/`var`) primary-constructor parameter stays in
scope for **every** property initializer in the class body, not just the one
textually next to it. If you rename `resolvedServiceFactory` back to
`serviceFactory` to "clean it up," every later property initializer that
references it (e.g. the `savedMonitor = SavedPrinterMonitor(..., serviceFactory)`
line) will silently re-resolve to the **nullable constructor parameter** instead
of your property, and you'll get a non-obvious type-mismatch compile error late
in the file, far from the actual cause. Leave the two names distinct.

Also: the constructor parameter is still called `serviceFactory` (not renamed)
specifically because ~18 existing test call sites use it as a **named argument**
(`PrinterModel(serviceFactory = { fake }, ...)`). Renaming the parameter breaks
every one of those. If you need to change this again, prefer adding new
parameters over renaming existing ones with named-arg call sites.

## Device / install gotchas (learned the hard way in earlier sessions, not this one)

- **Never run `installDebug` via Gradle** (or any Gradle task that chains through
  it) against a real device — it has wiped app data (saved printer profiles) in
  this project before. Always build with `./gradlew assembleDebug` and install
  with `adb install -r app/build/outputs/apk/debug/app-debug.apk` (the `-r` flag
  replaces without wiping data).
- Two real Motorola Razr phones are typically connected via `adb devices`: a
  "motorola razr 2026" and a "motorola razr 2023". **The Razr 2023 is the
  established evidence device** referenced throughout the roadmap docs
  (`UI_ACCEPTANCE.md`, `M1_ACCEPTANCE.md`, etc.) — target that one specifically
  with `-s <serial>`, don't assume which `adb devices` row it is each session
  (check `adb -s <serial> shell getprop ro.product.model`).
- Both Razrs are foldables with two physical displays; a plain
  `adb exec-out screencap -p` can fail with a "Multiple displays" warning and
  return non-image text. Use `adb shell dumpsys SurfaceFlinger --display-id` to
  list display IDs, then `screencap -p -d <id>`.
- Commit finished, verified work right away — don't wait to be asked. (This is
  the owner's standing preference from earlier sessions, not something re-derived
  here.)
