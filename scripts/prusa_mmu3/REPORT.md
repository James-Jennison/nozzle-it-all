## printer_notes and the engine's MMU3 ramming behaviour

The engine (WipeTower2.cpp l.1361) sets `m_is_mk4mmu3 = icontains(printer_notes, "PRINTER_MODEL_MK4") && icontains(printer_notes, "MMU")`. When on it: keeps linear advance on during ramming and turns it off for the cooling moves (= PS `enable_pressure_advance_during_ramming = true`), sets the nozzle to old-20 C for ramming (= PS `filament_ramming_temperature_delta = -20`), sends filament-monitoring off + `G4` 1.5 s before ramming and monitoring on after the change (= PS `filament_ramming_initial_delay = 1.5` + `stuck_filament_detection = 1`).

| pack | PS ramming delta / delay | PS stuck_filament_detection | PS enable_pressure_advance_during_ramming | markers added | engine flag |
|---|---|---|---|---|---|
| Prusa MK4S MMU3 | -20 / 1.5 | 1 | False | `PRINTER_MODEL_MK4SMMU3`<br>`PRINTER_MODEL_MK4`<br>`The MK4 marker enables WipeTower2 cold ramming and filament monitoring control for the MK4S MMU3.` | ON |
| Prusa MK3.9 MMU3 | -20 / 1.5 | 1 | False | `PRINTER_MODEL_MK3.9`<br>`PRINTER_MODEL_MK3.9MMU3`<br>`PRINTER_MODEL_MK4`<br>`The MK4 marker enables WipeTower2 cold ramming and filament monitoring control for the MK3.9 MMU3.` | ON |
| Prusa MK3.5 MMU3 | 0 (default) / 0 (default) | 0 | False | `PRINTER_MODEL_MK3.5MMU3`<br>`No MK4-family ramming marker on purpose (it must never be added to these notes): PrusaSlicer's MK3.5 MMU3 uses neither cold ramming nor the ramming delay nor stuck-filament monitoring.` | OFF |

Decision for MK3.5: PrusaSlicer gives MK3.5 MMU3 no -20 C / 1.5 s ramming values (the `*mmu specific*` fragment only matches `printer.base_model=~/(COREONE|MK4)/`), `stuck_filament_detection = 0` and `enable_pressure_advance_during_ramming = False`. With the flag OFF the engine disables linear advance before ramming (when `m_change_pressure`), does no cold ramming and no monitoring toggling - which matches all three PS values. So MK3.5 does **not** carry `PRINTER_MODEL_MK4`; its notes get `PRINTER_MODEL_MK3.5MMU3` (contains `MMU`, harmless without the MK4 marker).

**Known gap (MK4S / MK3.9):** the engine flag is all-or-nothing. PS MK4S/MK3.9 MMU3 want cold ramming + 1.5 s delay + stuck detection (flag ON gives these) but `enable_pressure_advance_during_ramming = False` (flag ON instead keeps LA on during ramming, which PS only does for CORE One and plain MK4). The engine has no `enable_pressure_advance_during_ramming`, `filament_ramming_temperature_delta`, `filament_ramming_initial_delay` or `stuck_filament_detection` option to express the difference. The packs follow the Orca CORE One MMU3 approach (flag ON), i.e. PA stays on during ramming on MK4S/MK3.9 - a deviation from PrusaSlicer.

Orca's CORE One MMU3 notes also contain `COREMMU` and `RAMMING_EXTRA`. Neither string is referenced anywhere in Orca's `src/` or in any other Orca profile (grep), nor in the engine, so they were not copied. `PRINTER_MODEL_MK4` is added explicitly (for MK4S it is already a substring of `PRINTER_MODEL_MK4S`).

## Things that could not be determined or have no engine equivalent

- **Load/unload split is an estimate.** PS has one `filament_change_time` (MK4S/MK3.9 19 s, MK3.5 27 s). Orca split CORE One's 19.8 s into 10.9 + 8.9; the same ratio (0.550505) was used, rounded to 0.01 s with unload = total - load: MK4S/MK3.9 10.46+8.54, MK3.5 14.86+12.14 (MK3.5's source pack had 17 + 16 = 33 s). Only print-time estimates use these values.
- **`enable_pressure_advance_during_ramming`**: no engine option (see the ramming section; MK4S/MK3.9 get LA-on-during-ramming from the MK4 marker although PS says False).
- **`multimaterial_purging`** (PS MK4S/MK3.9 80, MK3.5 140) and **`filament_purge_multiplier`** (PS Generic PLA MK4S/MK3.9 81.25%, MK3.5 100%): no engine option. The engine purges per `flush_volumes_matrix` x `flush_multiplier` (project/app-level; the Orca CORE One MMU3 profile does not set them either). The app should supply the flush matrix for the 5 slots; the PS numbers are the reference.
- **`stuck_filament_detection`** (PS MK4S/MK3.9 1, MK3.5 0): no engine option; covered only through the MK4 marker (M591 toggling around ramming).
- **`filament_ramming_temperature_delta` / `filament_ramming_initial_delay`**: no engine option; hard-coded -20 C / 1.5 s behind the MK4 marker (MK4S/MK3.9 ON = PS; MK3.5 OFF = PS defaults 0/0).
- **Abrasive-nozzle / high-flow checks in `M862.1`**: PS derives `A` from `filament_abrasive` of the used slots; the engine has no `filament_abrasive`/`nozzle_high_flow` option, so (as in Orca) `A`/`F` come from `ABRASIVE_NOZZLE`/`HF_NOZZLE` tokens in printer_notes. None of these packs has those tokens, so the generated G-code always sends `A0 F0` (a 0.4 brass/standard-flow nozzle). An abrasive-filament print will not raise the firmware's abrasive check.
- **Double `Tn` at print start**: the start G-code loads the first slot with `T[initial_tool]` (PS and Orca CORE One MMU3 do the same) and the engine then writes its own initial toolchange (`set_extruder(initial_extruder_id)`, GCode.cpp l.3129) for the same slot. Prusa firmware treats `Tn` for the already-loaded slot as a no-op as far as known, but this was not verified on hardware.
- **`color_change_gcode`** (PS `M600` + prime): no engine key; M600 colour changes are not part of an MMU pack.
- **`binary_gcode`, `remaining_times`, `variable_layer_height`**: PS-only, unchanged by MMU3, not mapped.
- **MK3.5 `retract_length_toolchange`** stays "2" (Orca MK3.5 value). PS `*common MK35*` sets `retract_length_toolchange 0` for both MMU and non-MMU, and Orca CORE One MMU3 has "0"; it is not an MMU3 delta in either source, so it was not changed - but with the MMU3 every tool change will retract 2 mm before the wipe-tower unload. Worth a test print.
- **MK3.5 `nozzle_temperature_initial_layer`** stays "220" (Orca). PS first_layer_temperature is 230 for MK3.5 with and without MMU3 (not an MMU delta). `nozzle_temperature` 220 -> 205 is the PS MMU3 absolute value; the PS non-MMU value is 225, so the PS MMU delta is -20 C relative to PS, -15 C relative to the Orca source value.
- **MK3.5 printer_model / MK3.5S**: PS `mk3.5mmu3` is named "Original Prusa MK3.5 & MK3.5S"; the pack is named MK3.5 MMU3 and uses `M862.3 P "MK3.5"` exactly as PS does.
- **Engine keys Orca uses that the engine lacks** (not written): `wipe_tower_type`, `printer_extruder_id`, `printer_extruder_variant`, `print_extruder_id`, `print_extruder_variant`.
- **Not verified on hardware or by slicing**: the script did not build or run the engine. The packs are profile data only; a test slice with 2+ filaments on each pack is the next step.
